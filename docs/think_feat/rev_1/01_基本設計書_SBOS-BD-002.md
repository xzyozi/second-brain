## 1. 概要と基本方針

### 1.1 文書の目的と対象範囲
本書は、クラウドLLM API（Claude Code, OpenAI GPT-4o等）に依存せず、完全なローカル環境（Ollama + オープンウェイトLLM）のみで動作する「第二の脳（Second Brain OS）」ソフトウェア開発・ナレッジ管理自律エージェントスタックの基本設計を定義する。
本システムは、ソフトウェアエンジニア個人が抱える未完成のアイデア、仕様上の疑問点、実装設計、コードの継続的リファクタリング、アルゴリズムのバックテスト計画といった機微な思考プロセスや業務データを一切外部サーバーへ送信することなく、ターミナル上の対話と自律的なバックグラウンド処理によって高品質なドキュメントおよび動作検証済みのコードへと昇華させることを目的とする。

特に今回の Rev.3.1 改版においては、従来の「LLMセッション内部での自動委譲とエージェント間連携」を完全に廃止し、**「Python側オーケストレーションによる決定論的制御」「自己修復ステートマシンと自動レビュー工程の最小侵襲統合」「母艦×衛星アーキテクチャによる Git スコープの完全隔離」「最小テスト通過単位へのタスク分解と依存順序制御」**を根底とする新設計を規定する。
本書は、本システムを導入・拡張・運用するすべてのエンジニアに向けた基本設計の正本であり、全体の論理レイヤー、コンポーネント構成、データフロー、権限セキュアモデルを徹底的に詳述するものである。

### 1.2 背景と解決すべき技術的課題・限界
従来のローカルLLMあるいはクラウドLLMを用いた自律コーディングエージェントやナレッジ管理スタックには、以下の重大な構造的課題および技術的限界が存在していた。

1. **ローカルLLMの知能・コンテキスト長制約による記憶喪失と迷子:**
   - 7B〜14Bクラスのローカルオープンウェイトモデルは、70B〜400B超のクラウド商用モデルと比較して、長文の文脈保持能力や複数命令の同時追従性に物理的な限界がある。
   - 長時間の壁打ちや複数タスクの連続処理を行うと、モデルが自身の現在の役割を見失う「思考スコープ汚染」が起きやすく、要件定義の議論中に唐突に不完全なコードブロックを出力したり、数ターン前の重要なアーキテクチャ制約を忘却する現象が頻発していた。
2. **エージェント間コンテキスト断絶とハルシネーションの増幅:**
   - 従来アーキテクチャでは、要件定義（Executor）からコード実装（Coder）へタスクを委譲する際、新しいLLMセッションが起動するため、前段のエージェントが対話を通じて構築した微細な制約や前提条件が失われていた。
   - コンテキストが断絶した状態でのコード実装は、プロジェクト内に存在しない独自のAPIやクラス、あるいは誤った引数構造を推測で補うハルシネーション（幻視）を強く増幅させ、実装の手戻りを幾度となく引き起こしていた。
3. **エラー伝搬・修復の非決定論性（退化モードの発生）:**
   - 構文エラーやテスト失敗時の再試行ループをLLM自体の「自律的判断」に委ねると、エラーログの根本原因を理解できず同じ間違いを無限に繰り返す、あるいは「テストを通過させるためだけにテストケース側を勝手に削除・改変する」という致命的な退化モードが発生していた。
4. **Gitサブモジュールと複数リポジトリ管理の破綻:**
   - LLMに対して Git Submodule やサブツリーの操作権限を付与すると、サブモジュールのポインタ更新ミスや Detached HEAD 状態、さらにはインデックスの不整合を正しく解消できず、親リポジトリと子リポジトリの双方を不可逆的に破壊するケースが多発していた。
5. **自己完了バイアスと客観的監査・レビューの不在:**
   - コード生成を行う実装モデル自身にその成果物の妥当性を評価させると、自身の出力に対する強い自己完了バイアスが働き、バウンダリ条件（境界値）の漏れ、例外処理の欠落、インジェクション等の脆弱性、仕様誤解をパスさせてしまう問題があった。

### 1.3 解決のための5大基本設計方針
本スタック（Rev.3.1）は、上記の技術的課題を根本から解消するため、以下の5大設計方針を貫徹する。

#### 方針1：Python側オーケストレーション化（決定論的外部制御の徹底）
LLMを「自律的に考え続けてタスクを完遂する万能エージェント」として扱うことをやめ、**「特定のコンテキストとプロンプトを受け取り、明確なフォーマットの文字列（JSONやMarkdownブロック）を返す純粋な関数コンポーネント」**として再定義する。
エージェントの呼び出し順序、コンテキストの注入、エラー分類、リトライ回数の制限、フォールバック判断は、すべて決定論的な Python スクリプト（`orchestrator.py` 等）のループと条件分岐によって明示的に外部制御する。

#### 方針2：母艦×衛星アーキテクチャによる Git スコープの完全隔離
Git Submodule を一切使用しない。システムOS（共通ルール、自動化ツール、エージェントプロンプト群）を格納する**母艦（`~/second-brain/`）**と、実際の開発対象であるプロダクト群のソースコードを格納する**衛星（`projects/<name>/`）**を完全に物理分離する。
母艦側の `.gitignore` により衛星サブディレクトリ（`/projects/*`）を Git の追跡対象から遮断し、LLMが衛星内でいかなるコミットやファイル変更を行っても、母艦側の Git ツリーが汚染されたり破壊されたりすることを100%防止する。

#### 方針3：最小テスト通過単位へのタスク分解と決定論的順序制御
大きな要件や機能追加を一度に一括実装させることを禁止する。「依存されない単一モジュール実装」→「既存ロジックからの接続呼び出し」→「結合テスト」という、**1回のコード生成と1回の自動テスト実行で必ず完結する最小単位（サブタスク）**へ事前に分解し、`tasks.md` に割り当てる。
後続タスクには先行タスクの依存ID（`<!-- blockedby:#ID -->`）をHTMLコメントメタデータとして埋め込み、オーケストレーターが依存の末端から順に1件ずつ安全に引き渡すことで、順序の破綻を防ぐ。

#### 方針4：自己修復ステートマシンへの「自動レビュー・監査層」の最小侵襲統合
既存の実装済みアセットである自己修復ステートマシン（`DRAFT` → `SANITIZED` → `L1_PASSED` → `L2_PASSED` → `L3_PASSED`）を破壊することなく、テスト通過後の新しい状態として **`REVIEW_PASSED`** を追加する。
実装モデル（モデルB: コード特化）とは異なる独立した推論・監査モデル（モデルA または モデルC: 推論特化）をレビュアーとして配置し、書き込み前後のコード差分（unified diff）と実装指示書を突き合わせ、客観的なコードレビューを自動実行する。

#### 方針5：無限ループ防止と人間への確実なエスカレーション（ブロッカー B7）
レビューによる差し戻しを無制限に繰り返して CPU/GPU リソースを消費することを防ぐため、タスク行内に `round:1 max_round:3` という回数制限メタデータを導入する。
最大試行回数（`max_round`）に達してもレビュー未通過で失敗した場合は、自動実行ループから即座に切り離し、人間による介入・判断を仰ぐ「ブロッカー B7（レビュー上限到達）」としてエスカレーションする。

## 2. システム全体論理レイヤー構成と論理アーキテクチャ

システムは明確に分離された5つの論理レイヤーと、それを支える永続化ストレージ層によって構成される。各レイヤーは疎結合に保たれ、インターフェースを介して決定論的に連携する。

```
+----------------------------------------------------------------------------------------------------+
| 【Layer 1: 対話・インタフェース層】 (OpenCode CLI / TUI / スラッシュコマンド)                         |
|   - Sisyphus Agent (直接対話・壁打ち・タスク分解・アイデアの構造化)                                  |
|   - PM Agent (新規プロジェクト発足・3大質問要件整理: /new-proj)                                      |
|   - ユーザーコマンドインターフェース: /orchestrate, /work <ID>, add-task.py                         |
+----------------------------------------------------------------------------------------------------+
                                                  │ (コマンド呼出 / 承認 ask / メタデータ更新)
                                                  ▼
+----------------------------------------------------------------------------------------------------+
| 【Layer 2: 制御・オーケストレーション層】 (Python Orchestrator Layer - tools/*.py)                   |
|   - orchestrator.py    : 中核ステートマシン・自己修復ループ・エラーエスカレーション制御               |
|   - score-issues.py    : 全プロジェクト横断4軸スコアリング (優先度・鮮度・工数・依存解決度)             |
|   - check-blockers.py  : 決定論的ブロッカー検知 (B1〜B7判定・依存ツリー評価)                         |
|   - context_manager.py : エージェント間コンテキスト共有・メモリ管理・トークン溢れ防止クリア           |
|   - agent_client.py    : OpenCode CLIサブプロセスラッパー・自動リトライ・レスポンスパース             |
|   - prompt_builder.py  : 動的プロンプト合成・エラーログ注入・言語フォーマット強制指示                  |
+----------------------------------------------------------------------------------------------------+
                        │                                                         │
                        ▼ (設計・実装指示)                                         ▼ (監査・レビュー指示)
+----------------------------------------------------+       +---------------------------------------+
| 【Layer 3: 決定論的検証・実行層】                    |       | 【Layer 4: 推論・監査レビュー層】     |
|   - ASTパーサー (構文木解析・非破壊自動コードマージ)   |       |   - Reviewer Agent (qwen3:32b等)      |
|   - Ruff / ESLint (静的解析・構文エラー検知・Linter)  |       |   - 仕様整合性・破壊的変更・脆弱性監査  |
|   - pytest / Jest (単体・統合テスト自動実行エンジン) |       |   - difflib.unified_diff 精密解析     |
+----------------------------------------------------+       +---------------------------------------+
                        │                                                         │
                        └────────────────────────────┬────────────────────────────┘
                                                     ▼ (決定論的ファイルI/O / 実行履歴記録)
+----------------------------------------------------------------------------------------------------+
| 【Layer 5: 永続化・ストレージ層】 (母艦×衛星 Git リポジトリ群 ＆ マークダウン/JSONファイルベース台帳)   |
|   - 母艦: ~/second-brain/ (AGENTS.md, roadmap.md, tasks.md, tools/*.py, .opencode/)                |
|   - 台帳: projects/.project-registry.json (プレフィックスと実ディレクトリパスの動的マッピング表)      |
|   - 履歴: tools/.cache/execution_history.json (1実行1レコード・レビュー指摘・品質監査ログ)           |
|   - 衛星: projects/<project-name>/ (独立Gitリポジトリ, project.json, README.md, tasks.md, src/)     |
+----------------------------------------------------------------------------------------------------+
```

### 2.1 レイヤー別責務とコンポーネント詳細

#### 1. Layer 1: 対話・インタフェース層
- **責務:** ユーザーとの自然言語による対話を担当。OpenCode のリッチな TUI (Terminal User Interface) およびコマンドライン引数を介して稼働する。
- **行動原理:** この層で動作するモデル（Sisyphus, PM）は「直接対話」のみを担当し、コードの直接書き込みやバックグラウンドのバッチビルド、Gitコミットの実行は一切行わない。ユーザーからの入力を受け止め、プロジェクトの要件やタスクリスト（`tasks.md`）の構造化データとして出力することに特化する。
- **主要機能:** `/new-proj` による新規プロジェクト発足時の質問生成、`add-task.py` による安全なタスク追記、`/orchestrate` による本日の推奨タスクの計画提示を行う。

#### 2. Layer 2: 制御・オーケストレーション層
- **責務:** 本自律スタックの中核エンジン。純粋な Python 3 コードによって実装され、LLMの非決定論的な動作を完全に包み込み、エラーの捕捉、タスク状態の更新、エージェントの順次呼び出しを決定論的にスケジュールする。
- **コンテキスト一元管理:** `SharedContext` を介して、要件定義・設計指示書・コード生成・エラーログといった中間アセットをメモリ上で引き継ぐ。各LLMセッションが単発で起動・終了しても、この層が文脈を保持し続けるため、ハルシネーションや文脈喪失が発生しない。
- **自己修復制御:** エラー分類器（`ErrorClassifier`）が検証層のログをスクレイピングし、構文エラー・仕様違反・テスト失敗・実行時例外・レビュー差し戻しを正確に分類して、最適化された修復プロンプトを再生成する。

#### 3. Layer 3: 決定論的検証・実行層
- **責務:** LLMの「主観」や「推測」を完全に排除し、ツール（Linter, Test Runner, Python `ast` モジュール）を用いた100%客観的で決定論的な検証およびコード変更を行う。
- **AST非破壊マージ:** 生成されたコードを文字列としてそのまま上書きするのではなく、Python の抽象構文木（AST: Abstract Syntax Tree）にパースした上で、既存関数やクラスと選択的にマージする。これにより、LLMが指示していない既存ロジックを勝手に削除する「破壊的変更」を完全に防止する。
- **高速フィードバック:** `ruff` や `pytest` の実行コードと標準エラー出力を即座に捕捉し、 Layer 2 の自己修復ループへ高速フィードバックする。

#### 4. Layer 4: 推論・監査レビュー層
- **責務:** すべての決定論的テスト（L3_PASSED）をクリアした後にのみ起動される、静的推論およびコード品質監査に特化したレイヤー。
- **客観的監査:** 実装を行った Coder（モデルB: 軽量高速モデル）ではなく、論理推論能力に特化した Reviewer（モデルAまたはモデルC: 32B以上推奨）が担当する。
- **非Git依存差分分析:** 人間によるコミット承認前のコードに対してレビューを行うため、 Git コミット履歴には依存せず、Python がメモリ上で計算した書き込み前後の unified diff と、設計指示書の仕様要件のみを突き合わせる。

#### 5. Layer 5: 永続化・ストレージ層
- **責務:** システムの状態、タスクの進捗、エージェントのログ、コードのバージョン管理を永続化する。
- **ファイルベース台帳:** データベース等の重い外部ミドルウェアを必要とせず、すべての状態は Markdown ファイル（`tasks.md`）、JSON 台帳（`.project-registry.json`）、NDJSON 履歴（`execution_history.json`）、そして Git ツリーという可読なファイル形式で保存される。これにより、エディタによる直接参照や grep スキャンが容易となり、高いポータビリティと耐障害性を維持する。

## 3. 母艦×衛星アーキテクチャの仕様と分離構造

### 3.1 複数リポジトリ管理とディレクトリ物理配置
本システムでは、Git Submodule の構造的欠陥（ポインタ不整合、Detached HEAD、再帰的クローンの複雑さ）を排除するため、「母艦の `.gitignore` による完全遮断 × 台帳インデックスによる動的パス探索」を採用する。

```text
~/second-brain/                             # 【母艦】システムOSリポジトリ (Git Root)
├── .git/                                   # 母艦自体のGitバージョン管理
├── .gitignore                              # ⭐ "/projects/*" を指定し衛星を物理遮断
├── AGENTS.md                               # 全エージェント共通行動規範・ルール定義書
├── roadmap.md                              # 母艦および全衛星を統括する中長期ロードマップ
├── tasks.md                                # 母艦システム自体の拡張・メンテタスクリスト
├── .opencode/
│   ├── opencode.json                       # OpenCode全体設定・マルチモデルマッピング定義
│   ├── commands/                           # スラッシュコマンド (/orchestrate, /work等)
│   └── agents/                             # エージェント別プロンプト (executor, coder, reviewer等)
├── tools/                                  # 決定論的自動化スクリプト群 (Python 3.10+)
│   ├── orchestrator.py                     # オートメーション中核ステートマシン・実行スクリプト
│   ├── score-issues.py                     # 横断スコア計算スクリプト
│   ├── check-blockers.py                   # ブロッカー検知スクリプト
│   ├── add-task.py                         # タスク安全追記スクリプト
│   ├── agent_client.py                     # OpenCode CLIラッパー
│   ├── context_manager.py                  # 共有メモリ・コンテキスト管理
│   ├── prompt_builder.py                   # プロンプト生成器
│   └── .cache/                             # 実行時キャッシュ・ログ (Git追跡対象外)
│       ├── priority-cache.json             # 算出済み優先度ランキングキャッシュ
│       ├── blocked.json                    # ブロッカー判定結果キャッシュ
│       └── execution_history.json          # 実行履歴・品質監査NDJSONログ
└── projects/                               # 【衛星管理領域】(母艦Gitから遮断)
    ├── .project-registry.json              # ⭐ 衛星台帳インデックス (キーと実パスの対応表)
    ├── ec-site/                            # 【衛星A】自社ECサイトリニューアルプロジェクト
    │   ├── .git/                           # 衛星A独自の完全独立Gitリポジトリ
    │   ├── project.json                    # 識別メタデータ (key: "EC", name: "ECサイトリニューアル")
    │   ├── README.md                       # プロジェクト仕様書・アーキテクチャ設計
    │   ├── tasks.md                        # 衛星Aのタスクリスト ([EC-001], [EC-002]...)
    │   └── src/                            # ソースコードディレクトリ
    └── fx-trading/                         # 【衛星B】FX自動売買・バックテストシステム
        ├── .git/                           # 衛星B独自の完全独立Gitリポジトリ
        ├── project.json                    # 識別メタデータ (key: "FX")
        ├── tasks.md                        # 衛星Bのタスクリスト ([FX-001], [FX-002]...)
        └── scripts/                        # バックテスト・データ収集スクリプト
```

### 3.2 プレフィックス（名前空間）制と動的ディレクトリ移管ロジック
全衛星プロジェクトの Issue ID が衝突することを防ぐため、必ずプロジェクトごとに一意の英数字プレフィックス（2〜5文字）を付与する。

1. **台帳インデックス (`projects/.project-registry.json`) の役割:**
   母艦と全衛星を接続する唯一の架け橋となるファイル。プレフィックスとパスをマッピングする。
   ```json
   {
     "EC": "projects/ec-site",
     "FX": "projects/fx-trading",
     "GRID": "projects/power-grid-calc",
     "SB": "."
   }
   ```
2. **動的パス移管プロセス (`/work <ID>` 実行時の挙動):**
   - ユーザーが `/work EC-012` またはバッチが `python tools/orchestrator.py execute --issue-id EC-012` を発火。
   - `orchestrator.py` のパーサーが ID からハイフン前段のプレフィックス `"EC"` を抽出。
   - `.project-registry.json` を参照し、対応する実ディレクトリパス `"projects/ec-site"` を取得。
   - Python 実行プロセスのカレントワーキングディレクトリ（CWD: Current Working Directory）および OpenCode CLI サブプロセスの実行パスを対象衛星ディレクトリへ動的に変更（`os.chdir`）する。
   - この移管により、後段の Linter, pytest, Ruff, および Git 操作はすべて対象の衛星プロジェクト内でのみスコープされ、母艦や他の衛星に干渉することがない。

## 4. 機能要件とコマンドインターフェース設計

### 4.1 プロジェクト発足・壁打ち機能 (`/new-proj`)
新規開発の着手を宣言した際、PM エージェント（`pm.md`）が立ち上がり、以下の3段階の質問を1問ずつ提示してユーザーの思考を構造化する。

| 質問フェーズ | 提示される内容・主眼 | ユーザー回答の整理目的 |
| :--- | :--- | :--- |
| **質問1：Why (目的と背景)** | なぜこのプロダクトを作るのか？解決したい具体的な痛みやビジネス上の課題は何か？ | プロダクトの存在理由と、仕様判断の迷いを防ぐ軸を明確化する。 |
| **質問2：MVP (最小実行可能製品)** | 最初の機能リリース（MVP）に絶対に不可欠なコア機能はどれか？何を切り捨てるか？ | 初期リリースのスコープを最小化し、不要な機能の作り込みを防ぐ。 |
| **質問3：Technical Concerns (技術的懸念)** | 性能要求、使用言語、外部依存API、セキュリティ要件で懸念されるリスクは何か？ | 実装前にアーキテクチャの制約条件を確定し、検証環境を設計する。 |

**回答完了時の自動生成アセット:**
- 対象ディレクトリ（例: `projects/<folder>/`）の自動作成と `git init` の実行。
- 構造化された `README.md`（目的、MVP機能仕様、技術構成）の生成。
- 識別メタデータ `project.json` の作成と、母艦 `.project-registry.json` へのプレフィックス自動登録。

### 4.2 タスク安全追記機能 (`add-task.py`)
LLMに `tasks.md` を無断で直接書き換えることを禁止する。タスクの追加は、必ず決定論的な Python スクリプトを介して行う。

#### コマンド仕様と実行例
```bash
# 1. 親タスク（新規機能ブロック）の登録
uv run python tools/add-task.py projects/ec-site "[EC-010] 決済トランザクション監視APIの実装" --priority high

# 2. サブタスク（分解された最小単位）の親IDバインド登録
uv run python tools/add-task.py projects/ec-site "[EC-011] ロールバック処理ログ記録モジュールの実装" --parent EC-010 --priority high

# 3. 依存関係（blockedby）の付与登録
uv run python tools/add-task.py projects/ec-site "[EC-012] ロールバック例外処理エラーハンドラの統合" --parent EC-010 --blockedby EC-011 --priority high
```

#### サブタスク階層化と行内メタデータ構造
生成される `tasks.md` は、LLMのセッション記憶に依存せず、HTMLコメント形式のメタデータによって親子関係と依存関係を完全に永続化する。
```markdown
## 未着手
- [ ] [EC-010] 決済トランザクション監視APIの実装  <!-- priority:high added:2026-07-27 -->
  - [ ] [EC-011] ロールバック処理ログ記録モジュールの実装  <!-- priority:high parent:EC-010 added:2026-07-27 round:1 max_round:3 -->
  - [ ] [EC-012] ロールバック例外処理エラーハンドラの統合  <!-- priority:high parent:EC-010 blockedby:#EC-011 added:2026-07-27 round:1 max_round:3 -->
```

## 6. セキュリティ、プライバシーおよび権限セキュアモデル

### 6.1 完全ローカル環境におけるデータ主権
本スタックにおいては、社外秘のソースコード、未公開のアルゴリズム（FX売買ロジックや電力網計算式等）、インフラ設計データ、および個人の思考メモが外部ネットへ送信されることは物理的にない。Ollama の `/v1` エンドポイントは `http://127.0.0.1:11434` に固定され、外部からのアクセスも firewall によって遮断されることを前提とする。

### 6.2 二重安全装置（Dual Safety Shield）設計
LLMによる暴走や不適切コードの実行を防ぐため、Python 側と OpenCode 設定側の双方で独立したセキュリティシールドを構築する。

#### 第1層：Python Orchestrator 事前静的検証モジュール
Coder が生成したソースコードをディスクのファイルへ書き込む直前に、`orchestrator.py` のセキュリティ検証関数が自動スキャンを実行する。
- **サプライチェーン攻撃の防止:** コード中に `pip install <package>` や `npm install <package>` 等の動的パッケージ導入が含まれている場合、Python の検証スクリプトが PyPI や npm のレジストリメタデータをスキャンし、**「公開から一定期間（例: 7日間）を経過していない新しいパッケージ」のインストールを強制拒否**する。
- **破壊的コマンドの検知:** `os.system("rm -rf ...")` や不審な外部ネットワーク接続（任意ドメインへのソケット通信やデータ送出）を正規表現パターンで検知し、即座に例外を送出してヒーリングループを停止する。

#### 第2層：OpenCode Permission コンフィグレーション
`.opencode/opencode.json` における `permission` セクションにて、ツール呼び出しとシェル実行の許可権限を以下のように厳格に制限する。
- **`edit`: `"ask"`** : 人間による直接の対話時におけるファイル編集は確認を求める。
- **`bash.*`: `"ask"`** : 一般的なシェルコマンドはすべて確認を必須とする。
- **`bash."python3 tools/*.py*"`: `"allow"`** : 決定論的な Python オートメーションスクリプト群の実行のみを自動許可し、バッチやループのノンストップ走行を可能にする。
- **`bash."git commit*"`: `"ask"`** : Git のコミットは絶対に自動化せず、ユーザーの明示的な確認と承認を必須とする。
- **`bash."rm -rf *"`: `"deny"`** : 広域な削除や親ツリーの消去コマンドは、いかなる場合も実行を完全拒否する。
