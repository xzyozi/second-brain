## 1. 概要
### 1.1 本章の位置づけ
本書は、3層自律アーキテクチャのうち、Layer 2「優先度判断ループ」の詳細設計を定義する。
元のループエンジニアリング思想では、`/orchestrate` コマンド1回でLLMが「スコアリング→ブロッカー検出→Issue連鎖実行→コミット」まで一気に行う。しかし、7B〜14Bのローカルモデルに同等の処理を委ねると、コンテキスト枯渇・役割の迷子・出力崩壊という失敗パターンが高確率で発生する。
本書はその解決策として**「判断処理（計算・正規表現）とLLM推論（対話・言語化）の完全な責務分離」**アーキテクチャを詳述する。

### 1.2 設計目標
1. ローカルLLMの知能限界・コンテキスト制約の中で、自律的優先度判断を再現する。
2. LLMには対話と清書のみを担わせ、スコア計算・ファイルI/Oは純粋なPythonスクリプトに委譲する。
3. 人間の確認ポイントを配置し、判断ミスによるリポジトリ破壊を防止する。

## 2. ローカルLLMにおける失敗パターン分析
### 2.1 失敗パターンA：コンテキスト枯渇による記憶喪失
Issueが増加し台帳が育つにつれて、プロンプトが16Kトークンを超え始める。Ollamaのデフォルト設定（num_ctx=4096）では数往復で文脈が失われる。

| 段階 | 症状 | 影響 |
| :--- | :--- | :--- |
| **初期（5Issue以下）** | 正常動作 | なし |
| **中期（10Issue前後）** | スコアリング途中でIssue内容を取り違える | 誤った優先順位付け |
| **後期（20Issue以上）** | 最初のIssueを完全に忘却・重複作業発生 | 実行結果の破綻 |

### 2.2 失敗パターンB：思考スコープ汚染（役割の迷子）
「スコアリング係」「ブロッカー検出係」「実行係」という複数の役割を1つのLLMセッションで連続して担わせると、ローカルモデルは役割を見失い、スコアリング中に唐突にコードを書き始める等の混乱を起こす。

### 2.3 失敗パターンC：曖昧ブロッカーの強行突破
「仕様不明確」「外部待ち」といったブロッカーをローカルモデルが自然言語推測で分類するのは困難であり、不完全な仕様のまま次のコード実装へ強行突破してしまう。

## 3. 設計：責務分離型優先度判断ループ
### 3.1 全体フロー
`/orchestrate` を「スコアリング(Python)→ブロッカー判定(Python)→計画提示(LLM)→実行確認(人間)」の4段階に分解する。

```text
 [トリガー] cron（毎朝 07:00）または手動 /orchestrate
        │
        ▼
 ┌────────────────────────────────────────────────────────┐
 │ Step 1: tools/score-issues.py（純粋計算・LLM不使用）   │
 │  ・全衛星の tasks.md と母艦 roadmap.md を横断パース    │
 │  ・4軸スコアを算出                                     │
 │  ・tools/.cache/priority-cache.json を出力             │
 └──────────────────────────┬─────────────────────────────┘
                            │
                            ▼
 ┌────────────────────────────────────────────────────────┐
 │ Step 2: tools/check-blockers.py（正規表現判定）        │
 │  ・ブロッカー6種(B1〜B6)を確定的に検出                 │
 │  ・tools/.cache/blocked.json を出力                    │
 └──────────────────────────┬─────────────────────────────┘
                            │
                            ▼
 ┌────────────────────────────────────────────────────────┐
 │ Step 3: /orchestrate（OpenCode / Agent: orchestrator） │
 │  ・バッシュコンテキスト注入構文(!`cat ...`)で読込      │
 │  ・実行可能な上位3件を抽出し人間向けの言葉で計画提示   │
 └──────────────────────────┬─────────────────────────────┘
                            │ ─── 人間の承認（permission: ask）
                            ▼
 ┌────────────────────────────────────────────────────────┐
 │ Step 4: /work <ISSUE_ID> (例: /work MOB-001)           │
 │  ・カレントディレクトリを対象プロジェクトへ動的移管    │
 │  ・1 Issue ずつ確実にコード生成・ステータス更新        │
 └────────────────────────────────────────────────────────┘

```

### 3.2 Step 1：スコアリング数式定義

| 軸 | 変数名 | 範囲 | 重み | 算出根拠 |
| --- | --- | --- | --- | --- |
| **優先度** | $P$ | 1〜5 | $\times 3.0$ | `critical`/`urgent`=5, `high`=4, `med`=3, `low`=2, `none`=1 |
| **鮮度** | $F$ | 0〜5 | $\times 2.0$ | 最終更新から：7日以内=5, 30日以内=3, 90日以内=1, 超=0 |
| **工数軽さ** | $E$ | 1〜5 | $\times 1.5$ | 見積もり：1h=5, 4h=4, 8h=3, 16h=2, それ以上=1 |
| **依存解決度** | $D$ | 0〜5 | $\times 2.0$ | ブロッカー数：0個=5, 1個=3, 2個=1, 3個以上=0 |

$$\text{Total} = (P \times 3.0) + (F \times 2.0) + (E \times 1.5) + (D \times 2.0)$$

$$\text{Score (0〜100)} = \frac{\text{Total}}{42.5} \times 100$$

### 3.3 Step 2：ブロッカー6分類ルール

| 分類ID | ブロッカー種別 | 検出パターン（正規表現） | 対応アクション |
| --- | --- | --- | --- |
| **B1** | 仕様不明確 | `仕様未確定|要確認|TBD|spec\?` | LLMに質問事項を列挙させる |
| **B2** | 依存Issue未完了 | `blockedby:\s*#\w+` | 先行Issueのスコアを繰り上げ |
| **B3** | 技術的調査未完 | `\[ \]\s*技術調査|spike:\s*open` | 調査タスクを最優先に昇格 |
| **B4** | レビュー待ち | `waiting.*review|PR.*open` | 人間へ通知のみ・スキップ |
| **B5** | 外部依存待ち | `waiting.*external|vendor` | スキップ・優先度最低化 |
| **B6** | リソース不足 | `resource:\s*missing|予算未確定` | 人間へ通知のみ・スキップ |

### 3.4 Step 3：コマンド定義 (`.opencode/commands/orchestrate.md`)

```markdown
---
description: 優先度スコアを元にIssue実行計画を提示する
agent: orchestrator
subtask: false
---

以下のスコアリング結果キャッシュを読み込んでください：
!`cat tools/.cache/priority-cache.json`

以下のブロッカー判定結果を読み込んでください：
!`cat tools/.cache/blocked.json`

**あなたのタスクはこれだけです：**
1. actionable（実行可能）なIssueのうちスコア上位3件を選ぶ。
2. 各Issueを1行で要約し、なぜその順番なのかを1文で説明する。
3. 以下のフォーマットで実行計画を出力する（それ以外は出力しない）：

```text
【本日の実行計画】
1位: [KEY-NNN]「タイトル」（スコア: XX.X）→ 理由1文
2位: [KEY-NNN]「タイトル」（スコア: YY.Y）→ 理由1文
3位: [KEY-NNN]「タイトル」（スコア: ZZ.Z）→ 理由1文

承認したら /work [KEY-NNN] から開始します。よろしいですか？

```

## 4. Layer 3 との接続点：cron連携
Layer 2のループはcronから自動起動することで、Layer 3「常時稼働」との接続点を形成する。ヘッドレス実行の安全対策として、朝イチは計算のみ自動実行し、計画承認以降はセミオートとする。

```bash
# crontab -e
0 7 * * * cd ~/second-brain && uv run python tools/score-issues.py && uv run python tools/check-blockers.py && uv run python tools/notify.py --event daily_summary

```
