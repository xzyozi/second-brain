## 1. 概要
### 1.1 文書の目的
本書は、クラウドAPI（Claude Code等）に依存せず、ローカル環境のみで動作する「第二の脳（Second Brain）」プロジェクト管理支援システムの基本設計を定義するものである。本システムは、エンジニア個人が抱える未完成のアイデアや業務上の悩みといった思考の生データを、外部のSaaS事業者に一切送信することなく、ターミナル上での対話形式によって構造化されたドキュメント（README、タスクリスト等）へと整理することを目的とする。
OSSのターミナル型AIコーディングエージェントである「OpenCode」と、ローカルLLM実行基盤「Ollama」を組み合わせることで、データプライバシーを完全に担保しながら、Claude Codeに匹敵する壁打ち体験を実現する。

### 1.2 背景と課題
近年、AIエージェントを活用したプロジェクト管理・要件整理ツールが普及しているが、その多くはクラウドAPIへの送信を前提としており、社外秘情報や個人の機微な思考過程が第三者のサーバーを経由する点に懸念が残る。一方で、完全にローカルで完結するLLM運用には、以下のような技術的課題が存在する。

#### Rev.2.0までの課題
* ローカルLLM（7B〜14Bクラス）はクラウドの大規模モデルと比較して知能・文脈保持能力に制約がある。
* Ollamaはデフォルトでコンテキスト長が4,096トークンに制限されており、長時間の壁打ちで文脈を喪失しやすい。
* ローカルLLMにファイル編集を直接行わせると、差分書き換えの破綻（内容の欠落・破壊）が発生しやすい。
* 対話の進行役なのか、ドキュメント清書係なのか、モデルが役割を見失う「思考スコープ汚染」が起きやすい。

#### Rev.3.0で対処する新たな課題
* **エージェント間コンテキスト断絶**: Executor→Coder等のエージェント連携時、新しいLLMセッションが開始され、前のエージェントが持っていた文脈が失われる。
* **ハルシネーションの増幅**: 各エージェントが独立したセッションで動作するため、互いの認識にズレが生じ、存在しない機能や要件を幻視しやすい。
* **エラー伝搬の困難**: 下流エージェント（Coder）で失敗した情報を、上流エージェント（Executor）が正確に把握できない。
* **Tool Calling制約の硬直性**: OpenCodeのPermission設定がセッション単位で適用されるため、細かいcooldown制御やサプライチェーン攻撃対策が困難。

### 1.3 設計方針

#### Rev.2.0までの方針
1. **クラウド互換性**：Claude Codeとの機能的な互換性を重視し、移行・併用コストを最小化する。
2. **責務の完全分離**：LLMには「思考の壁打ち」「対話の進行」のみを担わせ、ファイルへの確定的な書き込みは決定的なスクリプト（Python等）に委譲する。
3. **安全装置の標準化**：人間の承認を介さない自動コミット・自動破壊的操作を排除し、permission設定により安全性を確保する。
4. **複数リポジトリ管理**：システムOSである母艦と、成果物である衛星プロジェクトを `.gitignore` によってGitレベルで分離する。

#### Rev.3.0で追加する方針
5. **Python側オーケストレーション化**：エージェント間の連携ロジックをLLM内部から切り出し、Python側で明示的に制御する。各エージェントは「単発のLLM呼び出し」として扱い、コンテキストはPython側の共有メモリで管理する。
6. **エラーハンドリングの決定論化**：LLM任せのエラー処理を廃止し、Python側でリトライ・フォールバック・ロールバックを実装する。
7. **Tool Calling制約の外部化**：cooldown期間チェックやサプライチェーン攻撃対策をPython側で実施し、OpenCode Permissionは最小限の安全装置として保持する。
8. **テスタビリティの向上**：エージェント連携ロジックをPythonコードとして明示化することで、単体テスト・統合テストが可能になる。

## 2. システム全体構成
### 2.1 アーキテクチャ概要（Rev.3.0）

Rev.3.0では、エージェント間の連携制御をPython側に移管する。ユーザーからの直接対話は引き続きOpenCodeが担当するが、Issue実行等の自動化フローはPythonオーケストレーターが制御する。

```text
[ ターミナル ] ( ユーザー )
      |  ^
      |  | 直接対話・壁打ち (TUI)
      v  |
+--------------------------------------------+
| OpenCode  (直接対話のみ)                    |
|  - AGENTS.md（簡素化版）                    |
|  - .opencode/agents/  (プロンプトテンプレート)|
+------+-------------------------------------+
       | OpenAI互換API（単発呼び出し）
       v
[ Ollama API (localhost:11434/v1) ]
       |
       v
[ ローカルLLM (gemma4-12b-it-Q4_K_M 等) ]

+--------------------------------------------+
| Python Orchestrator Layer (新規)            |
|  - orchestrator.py     全体制御            |
|  - agent_client.py     OpenCode CLI呼び出し |
|  - context_manager.py  共有コンテキスト管理  |
|  - prompt_builder.py   プロンプト構築       |
+------+----------------------------+--------+
       | ファイルI/O / Git操作
       v
[ 母艦 Git リポジトリ ]
|- AGENTS.md / roadmap.md / tasks.md
|- tools/*.py (決定論的ロジック + オーケストレーション)
+- projects/<name>/ (衛星Git群)
    |- README.md
    +- tasks.md [PROJ-001]
```

#### アーキテクチャの変更点

| 項目                 | Rev.2.0                                 | Rev.3.0                               |
| -------------------- | --------------------------------------- | ------------------------------------- |
| **エージェント連携** | LLM内部で `opencode run --agent` を実行 | Python側で明示的に制御                |
| **コンテキスト管理** | 各LLMセッションが独立                   | Python側の `SharedContext` で一元管理 |
| **エラー処理**       | LLM任せ                                 | Python側でリトライ・フォールバック    |
| **Tool Calling制約** | OpenCode Permission                     | Python側で事前チェック + Permission   |
| **テスト可能性**     | ❌ 困難                                  | ✅ 単体・統合テスト可能                |

### 2.2 構成要素一覧（Rev.3.0更新版）

| 構成要素                    | 役割・概要                                                                              |
| --------------------------- | --------------------------------------------------------------------------------------- |
| **OpenCode**                | ターミナル型AIエージェント。直接対話とTUI提供。自動化フローはPython側に委譲。           |
| **Ollama**                  | ローカルLLM実行サーバー。OpenAI互換のREST API（`/v1`）を `localhost:11434` で公開する。 |
| **ローカルLLM**             | Gemma4-12B-IT、Qwen3.6-35B等、Tool Callingに対応したオープンウェイトモデル。            |
| **AGENTS.md**               | システムの基本ルール。Rev.3.0では簡素化し、Python側制御を前提とする。                   |
| **.opencode/agents/**       | エージェント別プロンプトテンプレート。Python側から動的に組み立てる素材として使用。      |
| **orchestrator.py** ⭐NEW    | Python側の統合制御エンジン。Issue実行の全体フローを管理。                               |
| **agent_client.py** ⭐NEW    | OpenCode CLI (`opencode run --agent`) の呼び出しラッパー。レスポンスパース機能を含む。  |
| **context_manager.py** ⭐NEW | 全エージェント間で共有するコンテキスト情報を管理（要件、制約、中間結果等）。            |
| **prompt_builder.py** ⭐NEW  | エージェント別に最適化されたプロンプトを動的構築。テンプレート + 実行時情報を統合。     |
| **tools/*.py**              | スコアリング、タスク追記等の決定論的Pythonスクリプト群（既存）。                        |
| **母艦×衛星Git**            | システムOS（母艦）と個別プロダクト（衛星）を独立管理するバージョン管理基盤。            |

## 3. 機能設計

### 3.1 プロジェクト発足・壁打ち機能 (`/new-proj`)

ユーザーが新規プロジェクトの着手を宣言した際、システムはPMペルソナとして3つの質問（Why／MVP／技術的懸念）を1問ずつ順番に提示し、回答が出揃った時点で内容を構造化して README.md に書き出す。

| 手順 | 主体     | 操作                                                      | 出力                               |
| ---- | -------- | --------------------------------------------------------- | ---------------------------------- |
| 1    | ユーザー | `/new-proj <folder名> <KEY>` を実行                       | コマンド起動                       |
| 2    | OpenCode | PMエージェント（pm.md）を起動                             | AGENTS.md読込・フォルダ自動生成    |
| 3    | PM       | 質問1（Why）を提示し待機                                  | ユーザー回答待ち                   |
| 4    | PM       | 質問2（MVP）を提示し待機                                  | ユーザー回答待ち                   |
| 5    | PM       | 質問3（技術的懸念）を提示し待機                           | ユーザー回答待ち                   |
| 6    | PM       | 回答を構造化し衛星に `README.md` と `project.json` を生成 | 台帳 `.project-registry.json` 登録 |

### 3.2 タスク追記安全機能 (`add-task.py`)

壁打ちの過程で発生したタスクは、LLMがMarkdownファイルを直接編集するのではなく、定型のPythonスクリプト呼び出しコマンドのみを提案する。

```bash
# フラット（親タスク）登録
uv run python tools/add-task.py projects/my-app "ユーザー認証APIの実装" --priority high

# サブタスク登録（親IDバインド）
uv run python tools/add-task.py projects/my-app "JWT検証ロジックの実装" --parent WEB-001 --priority high
```

#### サブタスク階層化（決定論的親IDバインド）

ローカルLLMのコンテキスト喪失に対抗するため、`--parent <親タスクID>` オプションによるサブタスクの階層構造化を導入している。LLMのセッション記憶に文脈を頼るのではなく、`tasks.md` のHTMLコメントメタデータ（`parent:<ID>`）に親子関係を物理的に保存する。

```markdown
## 未着手
- [ ] [WEB-001] ユーザー認証APIの実装  <!-- priority:high added:2026-06-28 -->
  - [ ] JWT検証ロジックの実装  <!-- priority:high parent:WEB-001 added:2026-06-28 -->
  - [ ] セッション管理の実装  <!-- priority:medium parent:WEB-001 added:2026-06-28 -->
```

この構造により、セッションが断絶しても各サブタスクがどの親Issueの文脈から生まれたかを100%一意に特定できる。

### 3.3 権限制御機能 (Permission)

OpenCodeのコンフィグにより、操作許可を細かく制御する。破壊的操作（`rm -rf *`）は `deny` とし、コミットおよびプッシュは必ずユーザー確認（`ask`）を介する。

### 3.4 Python側オーケストレーションフロー（Rev.3.0新規）

Issue実行の自動化フローをPython側で制御する。従来はExecutor→Coder間の連携をLLM内部で行っていたが、Rev.3.0ではPythonスクリプトがエージェントを順次呼び出す。

#### 3.4.1 Issue実行フロー

```python
# tools/orchestrator.py による制御例
def execute_issue(issue_id: str) -> ExecutionResult:
    """
    Issue実行の全体フロー
    1. 要件収集
    2. 制約検証
    3. 実装指示書生成
    4. コード生成
    5. ファイル書き込み
    6. テスト実行
    7. 結果記録
    """
    ctx = SharedContext()
    
    # Phase 1: 要件収集（Executor相当のLLM呼び出し）
    requirements = gather_requirements(issue_id, ctx)
    
    # Phase 2: 制約検証（Python側で決定論的処理）
    constraints = verify_constraints(requirements)
    ctx.add("constraints", constraints)
    
    # Phase 3: 実装指示書生成（ExecutorエージェントのLLM呼び出し）
    impl_plan = agent_client.call_agent(
        "executor",
        prompt_builder.build_implementation_prompt(requirements, constraints),
        context=ctx
    )
    
    # Phase 4: コード生成（CoderエージェントのLLM呼び出し）
    generated_code = agent_client.call_agent(
        "coder",
        prompt_builder.build_coding_prompt(impl_plan, constraints),
        context=ctx
    )
    
    # Phase 5: ファイル書き込み（Python決定論的処理）
    write_result = write_files(generated_code)
    
    # Phase 6: テスト実行（Python subprocess）
    test_result = run_tests(requirements.project_path)
    
    # Phase 7: 結果記録
    ctx.add_result(issue_id, test_result)
    return ExecutionResult(success=test_result.passed, context=ctx)
```

#### 3.4.2 コンテキスト共有の仕組み

従来は各LLMセッションが独立していたため、Executorで収集した要件をCoderが「忘れる」問題があった。Rev.3.0では`SharedContext`クラスで一元管理する。

```python
class SharedContext:
    """全エージェント間で共有するコンテキスト"""
    def __init__(self):
        self.requirements = {}
        self.constraints = {}
        self.intermediate_results = []
        self.error_history = []
    
    def add(self, key: str, value: Any):
        """コンテキストに情報を追加"""
        self.intermediate_results.append({
            "key": key,
            "value": value,
            "timestamp": datetime.now()
        })
    
    def get_summary(self) -> str:
        """プロンプトに埋め込む用のサマリー文字列を生成"""
        return f"""
        要件: {self.requirements}
        制約: {self.constraints}
        これまでの処理: {len(self.intermediate_results)}ステップ
        """
```

#### 3.4.3 エラーハンドリング戦略

LLM任せのエラー処理を廃止し、Python側で明示的に制御する。

| エラー種別                   | 検出方法                         | 対処                                            |
| ---------------------------- | -------------------------------- | ----------------------------------------------- |
| **LLM応答のパース失敗**      | JSON/Markdown構造検証            | 最大3回リトライ、失敗時は人間にエスカレーション |
| **コード生成の構文エラー**   | Pythonパーサーでの事前検証       | 構文エラー箇所を指摘してCoderに再生成依頼       |
| **テスト失敗**               | pytest終了コードの確認           | エラーログをCoderに渡して修正依頼（最大2回）    |
| **Tool Calling制約違反**     | Python側での事前チェック         | 警告を出力し、ユーザーに確認を求める            |
| **サプライチェーン攻撃検出** | cooldown期間チェック（Python側） | パッケージインストールを拒否                    |

## 5. 非機能設計

### 5.1 Rev.2.0までの設計
1. **セキュリティ・プライバシー**：全ての推論処理はlocalhost内のOllamaプロセスで完結し、外部ネットワークへのデータ流出を完全に防ぐ。
2. **可用性**：完全オフライン環境であっても全機能が100%継続動作可能である。
3. **拡張性**：決定論的処理をすべて `tools/` 配下のスクリプトに切り出しているため、将来的にAIモデルが大型化した際もプロンプト側の微調整だけで即座に対応できる。

### 5.2 Rev.3.0での改善

#### 5.2.1 信頼性の向上
- **エラー回復の自動化**: Python側でリトライロジックを実装し、一時的なLLM応答の不安定性を吸収する。
- **コンテキスト保全**: SharedContextによりエージェント間のコンテキスト断絶を防止し、ハルシネーションを抑制する。
- **決定論的検証**: コード生成後、Pythonパーサーやlinterで構文・スタイルを事前検証してから書き込む。

#### 5.2.2 保守性の向上
- **テスタビリティ**: 各コンポーネント（agent_client、context_manager等）を独立してテスト可能。
- **ログの体系化**: Python標準loggingで全フローをトレース可能にし、障害解析を容易化。
- **デバッグ性**: LLMプロンプトと応答をファイルに記録し、問題発生時の再現が容易。

#### 5.2.3 セキュリティ強化
- **サプライチェーン攻撃対策**: Python側でcooldown期間チェックを実装し、リリース直後のパッケージを自動拒否。
- **Tool Calling監査**: 全てのファイル書き込み・外部コマンド実行をログに記録し、事後監査を可能にする。
- **権限分離の徹底**: OpenCode Permissionは「最後の砦」とし、Python側で第一段階の検証を実施する。

#### 5.2.4 性能改善の余地
- **並列Issue処理**: Python側制御により、独立したIssueを並列実行可能（将来拡張）。
- **キャッシュ戦略**: 同じプロンプトに対するLLM応答をキャッシュし、冪等な呼び出しを高速化（将来拡張）。
