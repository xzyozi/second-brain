# LLMエージェント テスト設計指針（高度なテスト戦略）

自律型の大規模言語モデル（LLM）エージェントは、単純なテキスト生成の枠を超え、外部ツールの呼び出し、データベースの検索、APIとの連携、そして動的な計画立案（プランニング）を実行する複雑な分散システムへと進化しています。

しかし、これらのシステムのテストは、旧来のソフトウェアエンジニアリングのパラダイムに依存しているケースが多く、ユーザー視点でのブラックボックス的な受け入れテストに留まることが多い現状があります。この直感的なアプローチは、手動での評価を必要とし、自動化が困難であり、根本原因の分析（ルートコーズ分析）を妨げるだけでなく、高額なテスト環境の維持コストを引き起こします。

LLMエージェントの振る舞いは本質的に**非決定論的（Non-deterministic）**であり、同一の入力に対しても出力が変動します。この特性があるため、従来の完全一致を期待するアサーションに基づく単体テストは極めて脆弱であり、いわゆる「フレーキー（Flaky）なテスト」を量産する結果となります。

この問題を回避するために、外部のLLMプロバイダーを完全にモック（Mock）化し、静的なJSONを返すように設定するアプローチが存在します。しかし、LLMは外部サービスではなくアプリケーションの「コアロジック」そのものです。モデルの推論やツールの選択機能をモック化することは、ソートアルゴリズムのテストにおいて比較関数をハードコードされたリストに置き換えることに等しく、現実のプロダクトの挙動を全く検証できていない状態を生み出します。

## 構造的テスト（Structural Testing）の導入

このジレンマを解決するための中心的な戦略が、システムをコンポーネントごとに分解して検証する「**構造的テスト（Structural Testing）**」であり、その中核を担うのが「**スナップショットテスト**」および「**プレイバック（記録・再生）テスト**」です。構造的テストの導入により、テスト自動化ピラミッド、回帰テスト、テスト駆動開発（TDD）といったソフトウェアエンジニアリングのベストプラクティスをAIエージェントに適用することが可能になります。

LLMベースのエージェントにおける主要コンポーネントと、それらに対する構造的テストの要件は以下のように分類されます。

| コンポーネント | テストの根拠（Rationale） | サンプルテストの例 |
|---|---|---|
| **Agent core** | 初期化の動作確認、有効な設定か | 有効なモデルIDを用いてエージェントが正常に作成されるか |
| **Memory** | 存在とアクセスの確認、プライバシーの確保 | データの書き込み後に読み出しが可能か、他ユーザーのメモリへアクセスできないか |
| **Knowledge base** | 空データ・異常データへの対応、データの更新・拡張 | 空の文字列や長文を含むクエリのテスト。データを追加後、そのデータが検索結果に反映されるか |
| **LLM** | ファインチューニングされたモデルが機能するか | サンプルプロンプトに対して、微調整されたモデルが妥当な結果を返すか |
| **Tools** | 妥当な出力を返すか | `get_weather(Tokyo)` のようなツール呼び出しが妥当な形式の値を返すか |
| **Textual input** | ユーザー入力のバリデーション | プロンプトインジェクション、過度な長文入力、互換性のないフォーマットの検証 |

さらに、これらのコンポーネントが相互にどのように作用するか（例えば、プランニングモジュールとナレッジベースの連携）をテストすることも不可欠です。関連のない情報（Irrelevant information complexity）がプロンプトに混入しただけで、強力なLLMエージェントであっても平均27.3%のパフォーマンス低下を引き起こし、複数の複雑性が重なると最大63.2%の性能劣化を招くという研究結果も報告されています。

LLMを用いたAPI検証の自動化は、手動テストと比較して1回のAPIあたりわずか2.19ドルという低コストで実行可能であり、並列実行によるスケーラビリティも備えているため、自動化パイプラインの構築は経済的にも合理的です。

## トレースベースの記録と再生：SDKレベルのインターセプション

プレイバックテスト（Record/Replayテスト）は、エージェントが実行された際の実際の実行軌跡（トレース）を「カセット」として記録し、後続の継続的インテグレーション（CI）環境などにおいてその記録を再生することで、外部APIに依存せずに決定論的なテストを実現する手法です。

このアプローチは、従来のHTTPレベルのリクエスト・レスポンスをキャプチャするVCR（Video Cassette Recorder）型ツールとは一線を画します。AIエージェントのテストにおいては、HTTP通信というネットワークレイヤーではなく、**SDKレベルにおける「振る舞いのレイヤー」での記録・再生**が求められます。

例えば、TraceOps のようなフレームワークは、OpenAI、Anthropic、LangChain、LangGraph、CrewAIといったSDKの直下で動作をインターセプトし、実行トレース全体をYAML形式のカセットとして保存します。このカセットには、LLMへのリクエストだけでなく、ツール呼び出し、エージェントの意思決定、ストリーミングイベント、RAG（検索拡張生成）イベント、トークン数、コストなどのメタデータが詳細に記録されます。

### 軌跡の差分（Trajectory Diffing）と予算アサーション

SDKレベルでのインターセプションの真の価値は、単純な再生ではなく「**軌跡の差分（Trajectory Diffing）**」の検出にあります。

LLMエージェントにおける致命的な障害モードは、最終的な回答テキストが変化することではなく、推論パスが密かに変化していることです。システムが複雑化すると、モデルの変更や検索ステップのわずかな違いによって、余分なツール呼び出しを行ったり、不要な再試行ループに陥ったりすることがあります。最終的な回答が適切に見えたとしても、システムとしてはトークン消費が40%増加するなどの運用上のデグレ（機能低下）を起こしている可能性があります。

テスト実行時に以前のYAMLカセットと比較することで、以下のようなアサーションを実行できます：
- 以前よりも多くのツールを呼び出していないか。
- 使用されるモデルが意図せず変更されていないか。
- 実行ステップ数が増加していないか。
- トークンコストが急増していないか（Budget Assertions）。
- ワークフローの一部がサイレントにスキップされていないか。

また、意図的な変更（プロンプトの改善や新しいツールの追加）によって軌跡が変化した場合には、その差分をテストの失敗として扱うのではなく、新しいベースラインとして「承認」するレビュープロセスへの統合が可能です。このアプローチにより、開発者はAPIコールの反復コストをゼロに抑えつつ、決定論的なCI挙動を保証し、エージェントの推論プロセス（実行形状）を厳密に保存・検証することができます。

## フルスタックのモック化による非決定性の排除

2026年現在の最新のAIアプリケーションは、LLMだけでなく、複数の動的サービスと通信します。一般的なエージェントのリクエストは、LLM、MCP（Model Context Protocol）ツールサーバー、ベクトルデータベース、再ランク付け（Reranker）API、Web検索API、モデレーション層、そしてAgent-to-Agent（A2A）のサブエージェントなど、6〜7つの外部サービスを経由して処理されます。

CI/CDパイプラインにおいて決定論的なスナップショットテストを行うためには、これらすべての依存関係を制御下におく「**フルスタックのモック化**」が必要となります。これに対処するため、AIMock のような統合モックサーバーの導入が業界標準となりつつあります。これは単一のポートであらゆるエージェント通信を傍受し、事前に記録されたフィクスチャに基づいて応答を返すシステムです。

フルスタックモック化においてカバーすべき主要なサービスと機能は以下の通りです。

| モックコンポーネント | テスト対象と提供される機能 |
|---|---|
| **LLMock** | OpenAI、Claude、Geminiなど主要プロバイダーのAPIをシミュレート。ストリーミング、ツール呼び出し、構造化出力を単一のフィクスチャ形式に変換して再生する。 |
| **MCPMock** | ローカルのMCPサーバーをJSON-RPC 2.0経由でモック化し、データベースやファイルシステムへのライブなリクエストをバイパスしてツール出力を再生する。 |
| **A2AMock** | マルチエージェントシステムにおけるメッセージルーティングやSSEストリーミングをシミュレートし、特定のサブエージェントがダウンしている状態でのフォールバックをテストする。 |
| **VectorMock** | PineconeやChromaDBなどのベクトルデータベースをモック化。RAGパイプラインにおいて毎回完全に同一の検索結果を保証し、コンテキストの揺れを排除する。 |
| **Services Mock** | Tavily（Web検索）、Cohere（リランカー）、OpenAI Moderationなど、テストを不安定にする外部サービスからの応答を決定論的に固定する。 |

これらのインフラストラクチャは、初回の実行時に実際のライブAPIへのネットワーク通信を記録し、レスポンスのストリームを解析して静的なフィクスチャとしてディスクに保存します。特に、OpenAI SSE、Anthropic SSE、Ollama NDJSONなどの異なるストリーミングフォーマットを自動的に「コラプス（結合）」して保存する機能により、ネットワークの不安定性を排除し、2回目以降のCIテストを高速かつ完全に無料で実行することが可能になります。

また、ライブAPIの応答フォーマットの変更を24時間以内に検知する「ドリフト検出」や、HTTP 500エラーやTCP切断を意図的に引き起こす「カオステスト」を組み合わせることで、エージェントのレジリエンス（障害耐性）を検証できます。

## マルチターンおよびセッションレベルの再生テスト

単一のプロンプトと応答（シングルターン）の評価だけでは、実践的なエージェントの品質を担保するには不十分です。プロダクション環境における最も深刻な回帰は、ユーザーとのやり取りが数ターン進んだ後に発生します。例えば、ホテルの予約エージェントが、ユーザーが最終確認をする前に予約を実行してしまったり、数ターン前にユーザーが設定した制約条件を忘れてしまったりする事象です。これらは、1回の応答のみをチェックする単体のアサーションでは見過ごされやすいです。

解決策としては、ReplayGate のような概念を用い、「フライトレコーダー」のように実際の会話セッション全体を一度記録し、それを何度も再生してクロスターン（ターンをまたぐ）プロパティをアサーションするアプローチが求められます。

セッションレベルのテストでは、メッセージ、ツールの呼び出し、各ターン、そして会話全体を厳密なデータモデル（例：Pydanticのモデル群）として定義し、「**トレース契約（Trace Contract）**」を構築します。このデータモデルに対し、「指定したインデックスのターンより前にユーザーが確認を行っているか（`user_confirmed_before`）」といった、会話全体を俯瞰しなければ判断できない不変条件をテストします。

さらに、Webhook、WhatsApp、音声通話など、エージェントが実行される実際のチャネルにおけるメッセージの順序付け、チャンク化、セッションのタイムアウトといった要素もトレースの一部としてモデル化することで、理想化された関数呼び出しではなく、実際に起こった事象としての再生が可能となります。

AgentBenchのような多次元ベンチマークの分析によれば、LLMエージェントが複雑な環境で失敗する典型的な理由として、長期的な推論の失敗、意思決定の誤り、そして指示への非準拠が挙げられます。クロスターンでの再生テストは、これらの長期的な破綻を早期に発見するための要となります。

### AgentBenchにおける典型的な障害モード

セッションレベルでの再生テストを設計する際、システムがどのような形で破綻するかを分類・理解しておくことが重要です。AgentBenchの定義に基づく主要な障害モードは以下の通りです。

| 障害モード | 説明 |
|---|---|
| **Context Limit Exceeded (CLE)** | 対話履歴の長さがLLMの最大コンテキスト長を超過し、処理が継続できなくなる状態。 |
| **Invalid Format (IF)** | エージェントがシステムプロンプト等で指定された出力フォーマットの指示に従わず、後続のパース処理に失敗する状態。 |
| **Invalid Action (IA)** | フォーマットの指示には従っているものの、選択されたアクション（ツールの引数など）が論理的または環境的に無効である状態。 |
| **Task Limit Exceeded (TLE)** | 規定の最大対話ラウンド数に到達しても問題が解決されない、または同じ生成を無意味に繰り返す無限ループに陥る状態。 |

## レビュー駆動型テストと許容誤差（Tolerance）の導入

データサイエンス、機械学習、そしてLLMの出力は、従来のソフトウェアのように厳密な「正解（True）か不正解（False）か」のバイナリ判定に馴染みません。プロンプトを1つ変更しただけで、関連のない領域のテストが失敗したり、ハイパーパラメータの調整によって全体的なメトリクスが変動したりする、いわゆる「遠隔作用（Spooky action at a distance）」が頻発します。

このようなシステムにおいて、単なるPass/Failのテスト結果は「診断情報のないエラー（Computer says no）」を生み出し、開発者を混乱させます。これに対処するための戦略が、booktest のようなツールを用いた「**レビュー駆動型テスト（Review-Driven Testing）**」です。

### 読解可能なアーティファクトとしての出力管理

レビュー駆動型テストのフレームワークでは、テスト結果を単なる合否ではなく、人間が読解可能なMarkdownフォーマットのアーティファクト（テキスト、テーブル、Pandas DataFrame、画像など）としてキャプチャし、Gitなどのバージョン管理システムで追跡します。これにより、エージェントの振る舞いの変化をソースコードの差分（Diff）をレビューするのと同じように可視化できます。

変更が意図した改善であれば、開発者は対話的（Interactive）なモードで新しいスナップショットを「**承認（Accept）**」してベースラインを更新します。意図せぬ動作変更であれば「**拒否（Reject）**」し、回帰を防ぎます。

このプロセスにおいて、タイムスタンプや一時的なID（GUID）、スラッシュの方向（Windows vs POSIX）などの実行ごとに変わるノイズデータは、比較前に**正規化（スクラブ）**しておくことで、テストのフレーキーさを排除します。
